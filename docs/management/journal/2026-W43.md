# Journal — semaine 2026-W43 (du 19 octobre 2026 au 25 octobre 2026)

[2026-10-25] [PRO] IDs de villes Facebook : `CityFinder` v2 vérifié, colonne `cities.fb_location_id`, script `repair_fb_city_ids.py` → **codés, testés (250 tests dont l'application réelle contre un Postgres 16 local), poussés sur `ccr-92f47355-0yvnvx`** ; jamais exécutés contre le vrai Facebook à cette date. Plan : `plans/FB_CITY_IDS_AND_SCRAPER_HEALTH_PLAN.md`.
- **Décision de l'utilisateur** : « vérifier et changer tous les IDs qui ne sont pas bons dans la base et corriger la manière pour Facebook de les obtenir ».
- **`CityFinder` v2** (`backend/scraping/city_finder.py`, orchestration séparée de Playwright : `CityFinder.lookup` + `PlaywrightCityDriver`) : ne retient que les suggestions au nom exact et à la région absente ou compatible ; clique **par libellé**, attend que l'URL **change** et exige un ID numérique ; **sonde chaque ID candidat** (`/marketplace/<id>/` : ville affichée par le bouton de lieu, part de cartes « , QC », proximité si les coordonnées sont fiables) ; ne rend jamais un ID non vérifié (VERIFIED, sinon AMBIGUOUS / INDETERMINATE / NOT_FOUND → `None`). Sans province connue : ancien comportement signalé `LEGACY` (`needsReview`).
- **Pourquoi** : le clic sur une suggestion n'est pas fiable (deux suggestions différentes ont donné le même ID) et Facebook omet la région des lieux proches de l'IP — l'indice « Québec » ne correspondait donc jamais et la v1 retombait sur la 1re suggestion. Le bouton de lieu de l'ID français affichait lui aussi « Bromont » : seule la géographie des cartes le démasque.
- **`city_verification.py`** (fonctions pures, 37 tests) : `parse_label`, `filter_candidates`, `score_probe`, `decide` (proportions uniquement, **aucun minimum d'annonces** — Bromont est minuscule ; plancher de 3 cartes → INDETERMINATE, jamais une correction), `landed_name_matches`, `numeric_city_id`, `trusted_gazetteer` (écarte les coordonnées partagées par deux villes, ex. Sherbrooke = Montréal).
- **`cities.fb_location_id`** (colonne nullable, `schema.sql`) : ID Facebook réel ; `NULL` = `id` (convention historique). Plusieurs villes peuvent le partager (Saint-Hubert → Longueuil). `PostgresRepository.get_cities()` l'expose (`fbLocationId`), `bot.py::_run_facebook_scan` utilise `fbLocationId or id` pour chercher ; la clé de suivi de santé reste `cities.id`.
- **`add_city_auto`** : refuse l'ajout quand l'ID n'est pas vérifié (décision du 2026-10-05 tranchée) ; attache l'ID vérifié à une ville déjà au catalogue sous un autre identifiant (avant, l'ID trouvé était ignoré, donc un ID faux n'était jamais réparé) ; transmet coordonnées confirmées et gazetteer fiable à `CityFinder`.
- **`backend/scripts/repair_fb_city_ids.py`** : rapport JSON reprenable (dry-run, ancrages d'abord, pauses anti-bot 20–60 s et 3–5 min toutes les 5 villes, arrêt complet sur login/captcha) puis `--from rapport.json --apply` (transaction par ville, vérifie que la base n'a pas changé depuis le rapport, sauvegarde locale `cities_backup_*.json` en mode 600). Statuts `OK` / `ALIAS_OK` / `A_CORRIGER` / `AMBIGU` / `INDETERMINE` / `INTROUVABLE` / `ECHEC` ; seul `A_CORRIGER` est écrit. Coordonnées douteuses signalées, jamais modifiées.
- **Tests** : `test_city_finder.py` (20, faux pilote), `test_city_verification.py` (37), `test_repair_fb_city_ids.py` (25 dont application réelle en base et rapport avec faux Facebook), `test_pg_repository.py` (+4), `test_bot.py` (+8).
- **Limites** : sondage du fil général `/marketplace/<id>/` nouveau et non validé sur le vrai Facebook (validé le 2026-10-28 sur Bromont, voir W44) ; cartes du fil lues avec le même analyseur que les résultats de recherche (non vérifié que le lieu y est affiché de la même façon).
- **Couverture** : `journal/2026-W43.md`, `JOURNAL.md`, `TODO.md`, `reference/ARCHITECTURE.md`, `reference/DATA_FLOW.md`, `plans/FB_CITY_IDS_AND_SCRAPER_HEALTH_PLAN.md`.

[2026-10-23] [PRO] Suivi de santé des scrapers Facebook/Kijiji avec alerte à seuil (Phase A) et module pur de vérification des villes (Phase B1) → **codés, testés (19 tests purs + 9 `test_bot` + 5 base), poussés ; non déployés**.
- **Décisions de l'utilisateur** : Phase A d'abord ; alerte à **3 échecs de suite ou ≥ 50 % sur 10 scans**, 6 h entre deux alertes d'une même (source, ville) ; canal ntfy + email ; « un échec = le scraper est cassé, jamais aucune annonce ».
- **`backend/scrape_health.py`** (fonctions pures) : `classify_facebook` / `classify_kijiji` → `ok`, `no_cards` (0 carte), `geo_mismatch` (≥ 5 cartes et ≥ 90 % hors liste de villes), `blocked`, `detail_degraded` (≥ 3 fiches dont ≥ 50 % sans photo), `error` ; `should_alert` ; `repair_hint`.
- **Table `scrape_runs`** (`schema.sql`) : une ligne par scan de ville (source, ville, requête, résultat, cartes vues / hors liste / gardées, durée, `alerted_at`), **sans titre ni URL d'annonce**, purge à 90 jours. Méthodes `PostgresRepository.record_scrape_run`, `recent_scrape_outcomes`, `was_scrape_alerted_recently`, `last_ok_scrape_run`, `mark_scrape_run_alerted`, `purge_scrape_runs`.
- **Câblage** : `bot.py::_record_scrape_health` (jamais d'exception vers le scan ; un arrêt demandé n'est pas un échec), `NotificationService.notify_scrape_health` (ntfy + email, piste de réparation nominative), `FacebookScraper._scan_result["error"]` (l'exception interceptée n'était pas exposée), `KijijiScraper.last_scan` (blocage / erreur / cartes lues). Rapport : `backend/scripts/scrape_health_report.py`.
- **Limite connue** : un utilisateur qui n'a que 1 ou 2 villes en liste verrait presque toutes les cartes de sa zone « hors liste » → fausse alerte `geo_mismatch` ; piste : distinguer « hors région » de « hors liste ».
- **B1** : `backend/scraping/city_verification.py` (voir l'entrée du 2026-10-25).

- **Suite** : la comparaison anonyme / connecté devient la **Phase C** du plan (à reprendre avec le bon ID, connexion depuis le serveur par VNC pour passer le 2FA).
