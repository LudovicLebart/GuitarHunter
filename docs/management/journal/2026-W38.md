[2026-09-20] [PRO] Chantier H : corrige une fausse alerte "modèle Gemini indisponible" reçue en production suite à la bascule T1 Qwen, causée par une image Marketplace tronquée.
- **Symptôme réel signalé par l'utilisateur** : email d'alerte "MODÈLE GEMINI INDISPONIBLE — T1-qwen — Erreur : image file is truncated (5 bytes not processed)", suggérant à tort d'aller changer de modèle dans le panneau de configuration.
- **Cause racine n°1 (`backend/analyzer.py::_download_and_optimize_image`, code pré-existant)** : `Image.open()` ne lit que l'en-tête du fichier — le décodage réel des pixels (seul moment où une troncature se révèle) n'était forcé que pour les images RGBA/P (`.convert()`) ou dépassant `max_size` (`.thumbnail()`). Une image RGB de taille normale (le cas courant) sortait donc de la fonction sans jamais avoir été décodée ; la troncature n'était détectée que bien plus tard chez l'appelant qui force enfin la lecture des pixels (`img.save()` dans `_call_openai_compatible_json`), remontant comme un échec générique de l'appel T1 plutôt qu'un problème d'image. **Corrigé** : `img.load()` explicite ajouté dans le même bloc `try/except`, donc détecté et écarté au téléchargement comme n'importe quelle autre image invalide.
- **Cause racine n°2 (`_notify_model_unavailable`, ajoutée le jour même lors de la bascule)** : se déclenchait sur N'IMPORTE QUEL échec du décideur T1 réel, en réutilisant le message `notify_model_error` écrit spécifiquement pour une dépréciation de modèle Gemini ("va choisir un autre modèle dans le panneau de configuration") — contrairement à l'appel Gemini historique, qui ne déclenche cette alerte qu'après vérification via `_is_model_unavailable_error`. **Corrigé** : le déclenchement de `_notify_model_unavailable` est maintenant conditionné par `_is_model_unavailable_error(gatekeeper_reason)` ; tout autre échec (image, réseau, panne TokenRouter transitoire) envoie une nouvelle alerte distincte et honnête, `NotificationService.notify_gatekeeper_failure` (`backend/notifications.py`), qui ne présume pas la cause et n'invite pas à changer de modèle sans raison.
- **Validation** : reproduction en isolation (JPEG valide tronqué artificiellement) confirmant que `Image.open()` réussit silencieusement mais que `.load()` lève bien `OSError: image file is truncated` immédiatement — donc désormais capturé au bon endroit. `_is_model_unavailable_error` vérifié pour distinguer correctement les deux cas ("404 model not found" → vrai ; "image file is truncated..." → faux). `py_compile` + import sanity-check (stubs) OK.
- **Poussé sur `dev`** (`9d7fdaf`), aucune divergence avec `origin/dev` au moment du push.
