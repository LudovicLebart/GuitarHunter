# Journal — semaine 2026-W42 (du 12 octobre 2026 au 18 octobre 2026)

[2026-10-13] [PRO] Erreurs WebSocket sur mobile + synchronisation des annonces très longue → nouvelles annonces enfin notifiées, canal WS fiabilisé, relectures de l'index regroupées ; 66 tests API verts sur un Postgres 16 local jetable, `npm run build` OK, **non déployé**.
- **Symptômes (signalés par l'utilisateur)** : erreurs WebSocket fréquentes surtout après avoir quitté l'onglet sur le téléphone ; synchronisation si longue qu'il recharge la page. Plan relu par un second avis (Opus), qui a corrigé deux points du diagnostic initial et trouvé la cause principale.
- **Cause principale (nouvelle)** : une annonce NEUVE n'était jamais poussée au client. `create_new_deal` commit l'upsert `guitar_deals` (donc le `NOTIFY`) avant que `record_deal_match` n'écrive le lien utilisateur-annonce (autre transaction) : `_push_if_visible` ne trouvait aucune visibilité. Idem pour une annonce déjà connue qui entre dans le fil d'un autre utilisateur. Correctif : trigger `user_deal_matches_notify` (`schema.sql`, AFTER INSERT, même fonction/canal que `user_deal_state`). Test `test_websocket_pushes_when_deal_enters_user_feed` : **échoue sans le trigger, passe avec** (vérifié).
- **Diagnostic corrigé** : pas de ping à ajouter — `uvicorn[standard]` pings déjà (20 s / 20 s) ; un ping applicatif aurait même déclenché une relecture complète à chaque message (le client traite tout message ≠ `ready` comme un changement). Le timeout de 20 s (`API_TIMEOUT_MS`) ne couvre que le délai avant les en-têtes, pas le téléchargement.
- **Client (`apiService.js::openChangeSocket`, partagé par les 5 canaux)** : reconnexion immédiate au retour au premier plan (`visibilitychange`, `pageshow`, `online`) avec verrou `connecting` ; handlers liés au socket courant (l'`onclose` d'un ancien socket ne planifie plus de connexion en trop) ; timer de reprise annulé au nettoyage ; plus d'erreur affichée tant que la page est cachée ; rattrapage par une relecture si la page est restée cachée > 30 s avec un socket « ouvert ».
- **Client (`onDealsIndexUpdate`)** : une seule lecture de `/deals/index` à la fois, au plus une en attente, délai de regroupement de 300 ms (sans réarmement) — plus de réponse ancienne qui écrase une récente, plus d'empilement de GET sur l'unique worker.
- **Serveur (`main.py::ws_deals`)** : notifications regroupées par socket (250 ms, une requête `ANY($2)` au lieu d'une par notification — le pool est limité à 10), un message `{"type":"bulk"}` au-delà de 50 annonces visibles ; `add_termination_listener` ferme le WebSocket si la connexion Postgres `LISTEN` meurt (sinon socket ouvert mais muet).
- **À faire** : déployer (le trigger se crée au démarrage de l'API, `schema.sql` idempotent) puis valider sur mobile : quitter/revenir sur l'onglet, nouvelle annonce visible sans recharger. **Mesure encore à faire** : poids et durée de `GET /deals/index` (Wi-Fi et 4G) — n'envisager une synchronisation incrémentale (`?since=`) que si un téléchargement isolé reste lent. Pistes ultérieures (non faites) : `WHEN (OLD.* IS DISTINCT FROM NEW.*)` sur le trigger `guitar_deals`, sérialisation hors de la boucle d'événements, plusieurs workers uvicorn.

[2026-10-13] [PRO] Chat Gemini : « Failed to fetch (AI/error) » sur `gemini-3.1-pro-preview` → diagnostic par `llm_usage`, streaming du tour principal et reprise à 8 s ; `npm run build` OK, non testé avec le vrai Gemini.
- **Diagnostic** : `Failed to fetch` est un échec du `fetch()` avant toute réponse HTTP (pas un 429/5xx). Requête en lecture seule sur `llm_usage` (échecs du chat depuis la journalisation du 2026-10-06) : **2 lignes, toutes `connection`, un seul incident** (2026-10-13 02:21 UTC) — tour principal échoué après **108 s avec 0 photo** (donc pas la taille de la requête), puis reprise échouée en **95 ms** (réseau encore coupé 2 s plus tard). Profil d'une connexion coupée en pleine génération (Pro avec réflexion, silencieux ~2 min), pas d'un problème côté Google. Les échecs d'avant le 2026-10-06 n'étaient pas journalisés : une fréquence plus élevée avant cette date ne peut pas être exclue.
- **Correctif (`src/hooks/useDealChat.js`)** : (1) `sendLogged` utilise `sendMessageStream` : le flux est drainé puis `await stream.response` renvoie la même réponse agrégée — la cascade `functionCalls` / rappel de photo / propositions est inchangée ; délai de 120 s et annulation conservés. (2) `CHAT_RETRY_DELAY_MS` 2 s → 8 s.
- **Reste à valider en conditions réelles** : message simple, message avec photos, annonce achetée (propositions de restauration), annulation en cours de réponse. Si l'erreur revient : relever l'heure, l'appareil/réseau et le texte de la bulle (bouton Copier), puis relire `llm_usage` (`error_type`, `latency_ms`).
