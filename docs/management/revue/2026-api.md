# Constats de revue — section 6 : API FastAPI

Relevés le 2026-11-06 pendant la passe « deepdocument » (commit `d9f919e`), à la lecture de `main.py` en entier, de `auth.py`, `chat_claude.py`, `deals_repo.py`, `chat_repo.py`, `restoration_repo.py`, `users_repo.py`, `admin_repo.py` et des alertes. Rien n'a été corrigé. Format : voir [README](README.md). La plupart des constats de sécurité tiennent à un point : **l'inscription est ouverte** (le site propose `signUp`, `src/hooks/useAuth.js:65`), donc tout code qui fait confiance à « un utilisateur connecté » fait confiance à n'importe qui. À confirmer : que l'inscription est bien activée dans la console Firebase (l'API n'a aucune liste d'utilisateurs autorisés).

### R-6-1 — Le scan d'une adresse accepte n'importe quelle URL : le navigateur du serveur la visite
- Où : `POST /commands` (`main.py:187`, `type` et `payload` libres) → `bot.py::scan_specific_url` (`bot.py:1252` : `"kijiji.ca" in url.lower()`, sinon Facebook) → `scraping/core.py:683` (`page.goto(url)` avant le test de l'identifiant).
- Catégorie : sécurité · Gravité : haute (à confirmer par un essai contrôlé)
- Constat : aucune liste de domaines autorisés ni côté API ni côté bot. Un utilisateur connecté fait ouvrir au serveur, depuis son réseau privé (Tailscale, `localhost`, le Dell à `100.94.33.54`), n'importe quelle page. La navigation elle-même (un `GET` aveugle vers une adresse interne) est certaine. Une lecture du contenu est plus limitée : la fiche n'est acceptée que si l'URL finale contient `/marketplace/item/<chiffres>` (Facebook) ou un chemin `/v-…/<chiffres>` (Kijiji), ce qui suffit pour un serveur interne qui répond à n'importe quel chemin ; le texte lu est alors enregistré comme une annonce visible par l'utilisateur. Le test `"kijiji.ca" in url` est aussi satisfait par `http://autre.site/?kijiji.ca`.
- Piste : valider le domaine (`facebook.com`, `kijiji.ca`) et le schéma `https` dans l'API et dans le bot.

### R-6-2 — Une URL de photo ajoutée à une annonce partagée est téléchargée par le serveur et montrée à tous
- Où : `main.py:455` / `deals_repo.py:260-278` (`add_gallery_image`, aucune validation de `url`) ; lecture dans `bot.py:1742` (`storageImageUrls` en premier) et `analyzer.py:165-177` (`requests.get`, aucune restriction).
- Catégorie : sécurité · Gravité : haute à moyenne
- Constat : n'importe quel utilisateur qui voit une annonce peut y ajouter l'URL de son choix dans `storage_image_urls` de la ligne **commune**. Lors de la prochaine ré-analyse de l'annonce (par n'importe quel utilisateur), le bot télécharge cette URL (appel sortant depuis le réseau du serveur, comme R-6-1, mais aveugle) et la passe aux modèles comme une photo : une image piégée peut aussi tenter d'influencer l'analyse. Tous les utilisateurs chargent cette URL dans leur navigateur (suivi, contenu inapproprié). Même défaut, plus limité, pour `PATCH …/chat/{message}/gallery` (URL stockée dans le message).
- Piste : n'accepter que les URL du bucket Firebase Storage du projet, et filtrer côté téléchargement.

### R-6-3 — La configuration d'un compte n'est pas validée : fréquence, modèles, seuils, prompts
- Où : `main.py:111-133` (`UserConfigPatch`, `extra="allow"`), `users_repo.py:update_user_config` (fusion libre).
- Catégorie : sécurité / coût · Gravité : moyenne à haute
- Constat : tout compte peut écrire `scanConfig.frequency = 1` (un scan Facebook par minute depuis l'IP unique du serveur, au risque de faire bloquer tous les comptes), `max_ads`, `analysisConfig` (modèles, prompts, `activeSearchFamilies`, seuils `proTrigger*` : un seuil à 0 déclenche l'Expert sur chaque annonce). Seule la route d'administration impose `minutes ≥ 1`. Aucune borne haute nulle part.
- Piste : liste blanche de clés et bornes par clé côté API ; réserver les réglages de coût à l'administrateur.

### R-6-4 — Le chat Claude est une passerelle générique, sans quota par utilisateur
- Où : `chat_claude.py:30-38, 110-145` (le **système** et les **outils** viennent du client ; bornes par requête seulement), `main.py:645` ; `cost_alert.py` (alerte à 2 $ non bloquante, chat seulement).
- Catégorie : coût / sécurité · Gravité : moyenne à haute
- Constat : la docstring dit que l'endpoint « ne doit pas servir de passerelle Claude générique », mais le client choisit la consigne système (jusqu'à 40 000 caractères) et les outils. Une requête au maximum des bornes (≈ 400 000 caractères de texte, 40 images, 8 000 tokens de sortie) coûte de l'ordre de 0,3 à 0,5 $ (estimation, avec les tarifs de `llm_pricing.py`). Rien ne limite le nombre de requêtes par utilisateur ou par jour ; l'alerte prévient après coup et ne couvre que le chat.
- Piste : consigne système fixée côté serveur, plafond quotidien par utilisateur, refus au-delà d'un seuil global.

### R-6-5 — Le fil de chat d'une annonce est commun, et n'importe quel message peut s'y glisser
- Où : `chat_repo.py:34-37` (`WHERE deal_id`), `main.py:690-699` (`role` libre, `parts: Any` sans borne), schéma `deal_chat` sans `user_id`.
- Catégorie : sécurité / confidentialité · Gravité : moyenne (haute avec plusieurs utilisateurs réels)
- Constat : confirme R-1-2 côté API. Deux utilisateurs qui voient la même annonce lisent les messages l'un de l'autre. Comme `role` et `parts` sont libres, un utilisateur peut écrire un faux message de rôle `model` dans le fil ; le navigateur de l'autre le rejouera au modèle comme historique (injection), et rien ne borne la taille stockée.
- Piste : `user_id` sur `deal_chat`, rôles limités à `user`/`model`, taille maximale.

### R-6-6 — Tout utilisateur connecté peut écraser le partage public de n'importe quelle annonce
- Où : `main.py:1187-1190` (`PUT /shared-deals/{id}`), `shared_repo.py:10-18`.
- Catégorie : sécurité · Gravité : moyenne
- Constat : aucun contrôle de visibilité ni de propriété, aucune borne de taille ; `GET /shared-deals/{id}` est public. L'identifiant est celui de l'annonce Facebook. Un compte peut remplacer le contenu affiché derrière un lien de partage existant (défiguration), ou publier du contenu arbitraire sous un identifiant au choix. Le commentaire du code l'indique comme un reflet des anciennes règles Firestore.
- Piste : garder le créateur (`created_by`) et n'autoriser que lui, ou signer le partage.

### R-6-7 — Les jetons ne sont pas contrôlés contre la révocation, les sockets ne sont jamais ré-authentifiées, le jeton est dans l'URL
- Où : `auth.py:35, 55` (`verify_id_token` sans `check_revoked`) ; `main.py` WebSocket (vérification à la connexion seulement) ; `?token=` dans l'URL.
- Catégorie : sécurité · Gravité : moyenne
- Constat : un compte désactivé ou dont le mot de passe a changé garde l'accès jusqu'à l'expiration du jeton (1 h), et une socket ouverte continue de recevoir des notifications sans limite de durée. Le jeton en paramètre d'URL apparaît dans les journaux d'accès (uvicorn, Tailscale Funnel). Le jeton est valide pour la durée d'un jeton Firebase même si l'utilisateur est supprimé de `users` ; `POST /users/me` le recrée.
- Piste : `check_revoked=True` pour les routes sensibles ; durée maximale d'une socket ; envoyer le jeton dans un premier message plutôt que dans l'URL.

### R-6-8 — Une connexion Postgres dédiée par socket, hors pool
- Où : `main.py:146, 513, 791, 999, 1125` (`asyncpg.connect` par WebSocket).
- Catégorie : robustesse · Gravité : moyenne (à mesurer)
- Constat : chaque utilisateur ouvre jusqu'à trois sockets permanentes (config, annonces, villes) plus une par chat ou plan ouvert, chacune avec sa connexion `LISTEN`. Avec deux instances (test et production), 20 utilisateurs représentent plusieurs dizaines de connexions, avant les pools de l'API (10 chacune) et du bot (10). `max_connections` de Postgres n'a pas été relevé.
- Piste : un seul écouteur par processus qui distribue aux sockets (déjà fait pour `index_version`).

### R-6-9 — Une annonce supprimée de Postgres verrouille son achat pour tout le monde
- Où : `deals_repo.py:187-221` (`toggle_purchased`), `schema.sql:68` (`purchased_by_user_id … ON DELETE SET NULL`), `admin_repo.py:111-120`.
- Catégorie : bug · Gravité : moyenne (confirmé par lecture du SQL)
- Constat : quand l'administrateur supprime un utilisateur, les annonces qu'il avait achetées gardent `is_purchased = true` avec `purchased_by_user_id = NULL`. Le `UPDATE` de `toggle_purchased` exige `NOT is_purchased` ou « acheteur = moi », donc il ne trouve aucune ligne et la route répond « achetée par un autre utilisateur » (409) à tout le monde, pour toujours. Complète R-1-1.
- Piste : à la suppression d'un utilisateur, défaire ses achats, ou autoriser un administrateur à les libérer.

### R-6-10 — Valeurs non bornées sur plusieurs écritures
- Où : `analysis-overrides` (`deals_repo.py:281-312` : scores `SMALLINT` sans bornes 0 à 10, pas de contrôle de type → erreur 500), `POST /deals/by-ids` (liste d'ids sans limite), `kijiji-radius` (valeur négative ou immense), `purchasePrice`, `parts` du chat, `snapshot` partagé, `RestorationItemCreate.label`.
- Catégorie : robustesse · Gravité : basse à moyenne
- Constat : l'interface valide ces valeurs avant d'appeler (par exemple les scores d'une requalification), pas le serveur. Un client autre que le site, ou un bug, écrit des valeurs que les statistiques ne savent pas traiter.
- Piste : modèles Pydantic avec `Field(ge=, le=, max_length=)`.
