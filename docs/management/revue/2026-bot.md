# Constats de revue — section 2 : bot (orchestration)

Relevés le 2026-11-05 pendant la passe « deepdocument » (commit `22e5a1b`), à la lecture de `main.py`, `backend/bot.py`, `backend/services.py`. Rien n'a été corrigé. Format : voir [README](README.md). Les constats marqués « à confirmer » demandent un test ou une lecture de production avant correction.

### R-2-1 — Le planificateur `schedule` est global : partagé par tous les utilisateurs et tous les threads
- Où : `backend/services.py:105-122` (`schedule.every(...)`, `schedule.clear('scan')`, `schedule.run_pending()`), `main.py:93` et `main.py:316`.
- Catégorie : bug · Gravité : haute dès qu'il y a plus d'un utilisateur ou un redémarrage de thread
- Constat : la bibliothèque `schedule` n'a ici qu'un seul planificateur pour tout le processus. Chaque `TaskScheduler` y ajoute ses jobs (scan, nettoyage, purge) liés à **son** bot. Conséquences :
  1. `update_scan_frequency` d'un utilisateur appelle `schedule.clear('scan')` : cela supprime le job de scan de **tous** les utilisateurs et ne remet que le sien.
  2. `run_pending()` est appelé par chaque thread utilisateur **et** par le thread principal (watchdog) : le scan d'un utilisateur peut s'exécuter dans le thread d'un autre, ou dans le thread principal, dont il bloque alors le watchdog pendant toute la durée du scan.
  3. Quand le watchdog redémarre un thread mort, le nouveau `TaskScheduler` ajoute de nouveaux jobs sans retirer ceux de l'ancien bot : l'ancien bot (objet périmé) continue d'être planifié, d'où des scans en double.
  4. Les jobs d'un utilisateur retiré de Postgres restent planifiés.
  5. `run_pending` n'est pas protégé contre l'appel simultané depuis plusieurs threads : un job peut s'exécuter deux fois.
- Piste : un `schedule.Scheduler()` par bot (instance dédiée), ou un minuteur par bot sans bibliothèque ; retirer les jobs à l'arrêt d'un bot.
- À confirmer : nombre d'utilisateurs réels actifs en production et fréquence des redémarrages de threads.

### R-2-2 — « Arrêter le scan » ne peut pas interrompre un scan planifié exécuté dans la boucle de l'utilisateur
- Où : `main.py:93` (`scheduler.run_pending()` dans `main_loop`) et `main.py:121-135` (commandes de réveil de pause exécutées de façon synchrone, lignes 179-188).
- Catégorie : bug · Gravité : moyenne (à confirmer)
- Constat : un scan planifié s'exécute **dans le thread de la boucle** qui lit les commandes. Pendant ce scan (plusieurs minutes), aucune commande n'est lue : `STOP_SCAN` et `STOP_BOT` ne posent leur événement qu'une fois le scan terminé, donc ne l'interrompent pas. Seuls les scans lancés par `REFRESH` (thread séparé) sont interruptibles. À cause de R-2-1, le scan peut aussi tourner dans le thread d'un autre utilisateur, ce qui rend le comportement imprévisible. Même défaut pour une commande reçue pendant la pause : elle s'exécute dans la boucle.
- Piste : exécuter les scans planifiés dans un thread dédié, comme `REFRESH`.

### R-2-3 — Le sémaphore de navigateurs est gardé pendant l'analyse IA
- Où : `backend/bot.py:814-943` (Facebook : permis pris avant le scraper, rendu après `_dispatch_analysis_batch`) ; `bot.py:1107-1207` (Kijiji : un permis pour tout le cycle, analyse comprise).
- Catégorie : performance · Gravité : moyenne
- Constat : `MAX_CONCURRENT_BROWSERS` (3) plafonne les navigateurs, mais le permis reste occupé pendant l'analyse des annonces d'un ancrage (appels IA de 5 à 25 s, 5 en parallèle), alors que le navigateur ne sert plus. Avec plusieurs utilisateurs, les scans, nettoyages et `SCAN_URL` (attente de 300 s puis abandon) se bloquent pour rien.
- Piste : collecter les annonces, fermer le scraper et rendre le permis, puis analyser.

### R-2-4 — Chaque annonce trouvée relit tout le catalogue pour détecter un doublon inter-plateforme
- Où : `backend/bot.py:304` (`self.repo.get_deals_index_snapshot()` dans `_find_cross_platform_duplicate`), `backend/pg_repository.py:141-159`.
- Catégorie : performance · Gravité : moyenne
- Constat : pour chaque annonce, un `SELECT` de 6 colonnes sur toute la table `guitar_deals` (≈ 8 500 lignes) puis une boucle Python (Jaccard sur les titres). Jusqu'à 5 annonces en parallèle, plusieurs fois par cycle. `_build_city_display_names` relit aussi tout le catalogue pour de simples libellés.
- Piste : requête SQL filtrée sur le prix (index) et la source ; ou instantané lu une fois par cycle.

### R-2-5 — La file de ré-analyse est globale et sans réservation
- Où : `backend/pg_repository.py:176-184`, `main.py:30-40` (un `monitor_retries` par utilisateur), `bot.py:1385-1422`.
- Catégorie : bug / coût · Gravité : moyenne
- Constat : chaque thread utilisateur lit toutes les annonces `retry_analysis` (`SELECT *`, `ai_analysis_raw` compris) toutes les 5 s, sans les réserver. Deux utilisateurs peuvent donc analyser la même annonce en même temps (double appel de modèle, écritures concurrentes). `REANALYZE_ALL` d'un utilisateur met aussi en file des annonces partagées avec les autres.
- Piste : réserver par `UPDATE … SET status = 'analyzing' … WHERE status = 'retry_analysis' … RETURNING`.

### R-2-6 — La ré-analyse peut déclasser une pépite
- Où : `backend/bot.py:587-601` (garde-fou seulement dans `handle_deal_found`, sur changement de prix) contre `bot.py:1415-1417` (`process_retry_queue`) et `bot.py:1752-1756` (`analyze_single_deal`).
- Catégorie : bug probable · Gravité : moyenne (à confirmer par test)
- Constat : le commentaire du garde-fou dit que le Portier local n'est pas déterministe et qu'une `PEPITE` ne doit jamais devenir `NOT_PROMOTED`. Les ré-analyses en file (`REANALYZE_ALL`) et manuelles écrivent le résultat sans ce contrôle.
- Piste : mettre le garde-fou dans une fonction commune.

### R-2-7 — Les commandes en attente sont rejouées après un redémarrage
- Où : `backend/services.py:66-68` (« On ne vérifie pas les commandes lors de l'initialisation ») ; `main.py:94`.
- Catégorie : doc-code / comportement · Gravité : basse
- Constat : `initial=True` n'est utilisé que dans le constructeur. Au premier tour de la boucle (5 s plus tard) toutes les commandes `pending` sont lues. Une commande longue qui n'était pas terminée au redémarrage (déploiement) est donc rejouée, y compris `REFRESH` et `REANALYZE_ALL`. Le commentaire affirme le contraire.
- Piste : décider si le rejeu est voulu (alors corriger le commentaire) ou marquer les commandes périmées.

### R-2-8 — Un bot retiré reste vivant et le watchdog ne temporise pas
- Où : `main.py:324-331` (retrait), `main.py:147-177` (pause), `main.py:339-369` (redémarrage).
- Catégorie : robustesse · Gravité : basse
- Constat : retirer un utilisateur pose `stop_event` mais ne joint pas le thread : il entre en pause de 12 h, puis repart en `idle` et continue à tourner (thread, `monitor_retries`) pour un utilisateur supprimé. Le redémarrage d'un thread mort n'a aucune temporisation (une boucle d'échec relance un bot toutes les 30 s), et `GuitarHunterBot(...)` y fait des appels Firebase et Postgres dans le thread principal.
- Piste : un événement d'arrêt définitif distinct de la pause ; temporisation exponentielle.

### R-2-9 — La notification part avant l'écriture en base
- Où : `backend/bot.py:602-622`.
- Catégorie : robustesse · Gravité : basse
- Constat : `notify_deal` est appelé avant l'envoi des photos vers Storage et avant `create_new_deal`. Si l'un des deux échoue, l'annonce n'est pas marquée traitée, sera retentée au cycle suivant et notifiée une seconde fois.
- Piste : notifier après l'écriture.
